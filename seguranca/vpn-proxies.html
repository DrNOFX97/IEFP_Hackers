VPN & Proxies

Esconder, proteger e intermediar. VPNs e proxies são duas formas de interpor um intermediário entre o utilizador e a Internet, mas resolvem problemas diferentes. Nesta aula, exploramos como funcionam, que tipos existem, quando usar cada um e que mitos convém desfazer.

01 — Enquadramento

Dois intermediários, dois propósitos

Tanto uma VPN como um proxy colocam um intermediário entre o cliente e o destino. A diferença está na profundidade da intermediação: um proxy atua tipicamente a nível de aplicação e apenas para tráfego específico; uma VPN cria um túnel a nível de rede que captura todo o tráfego do dispositivo.

🔐

VPN

Virtual Private Network
  • Cria um túnel cifrado entre o dispositivo e um servidor VPN.
  • Captura todo o tráfego — HTTP, DNS, VoIP, jogos, tudo.
  • O destino final vê o IP do servidor VPN, não o do utilizador.
  • O operador da VPN vê o tráfego (a menos que seja no-logs).
  • Usada para privacidade, acesso remoto e contornar censura.
🔀

Proxy

Servidor intermediário
  • Intermedeia pedidos de aplicações específicas (browser, cliente).
  • Não captura todo o tráfego do sistema, só o configurado.
  • Pode ou não cifrar a comunicação com o cliente.
  • Versátil: cache, filtragem, anonimização, inspeção.
  • Usado para controlo, desempenho e privacidade parcial.
ℹ️
A analogia do túnel e do mensageiro

Uma VPN é como um túnel privado construído entre a sua casa e um ponto remoto: tudo o que entra no túnel viaja protegido e ninguém pelo caminho consegue ver o que vai lá dentro. Um proxy é como contratar um mensageiro para entregar as suas cartas: ele leva-as ao destino, mas cada carta é tratada individualmente, e ele pode ler o que vai em cada uma.

02 — Virtual Private Network

VPN em detalhe

Uma VPN estabelece um túnel cifrado entre o dispositivo do utilizador e um servidor remoto. Todo o tráfego de rede do dispositivo é encaminhado por esse túnel, tornando impossível para um observador na rede local ver o conteúdo ou o destino real.

Tipos de VPN essencial

01

VPN de acesso remoto (Remote Access VPN)

Também designada client-to-site. Um utilizador individual liga-se a uma rede corporativa a partir de casa, de um hotel ou de um café. É o tipo mais comum em teletrabalho e o que a maioria das pessoas conhece como "usar a VPN".

# Exemplo: ligação a uma VPN OpenVPN a partir da linha de comandos $ sudo openvpn --config escritorio.ovpn TLS: Initial packet from [AF_INET]203.0.113.42:1194 VERIFY OK: depth=1, CN=Empresa CA Initialization Sequence Completed ^ túnel estabelecido; todo o tráfego passa pelo servidor da empresa
02

VPN site-to-site

Liga duas redes inteiras — por exemplo, o escritório de Lisboa ao do Porto. Os routers de cada lado estabelecem o túnel e todo o tráfego entre as duas redes passa por ele, de forma transparente para os utilizadores.

# Exemplo: túnel IPsec entre dois routers (configuração conceptual) conn lisboa-porto left=203.0.113.10 # IP público do router de Lisboa leftsubnet=10.1.0.0/24 # rede interna de Lisboa right=198.51.100.20 # IP público do router do Porto rightsubnet=10.2.0.0/24 # rede interna do Porto ike=aes256-sha2_256-modp2048! esp=aes256-sha2_256! keyexchange=ikev2 auto=start
03

VPN comercial / consumer

Serviços como Mullvad, ProtonVPN ou IVPN vendem acesso a servidores VPN distribuídos pelo mundo. O objetivo principal é privacidade face ao ISP e à rede local, e por vezes contornar bloqueios geográficos. A confiança desloca-se do ISP para o operador da VPN.

# Verificar se a VPN está ativa (o IP público deve ser diferente do ISP) $ curl -s https://ifconfig.me 185.65.134.42 ^ este IP pertence ao servidor VPN, não à ligação doméstica $ curl -s https://ipinfo.io/185.65.134.42 { "city": "Stockholm", "country": "SE", "org": "M247 Europe SRL" }
04

VPN pessoal (self-hosted)

Montar o próprio servidor VPN — em casa, numa VPS ou num Raspberry Pi — para acesso remoto à rede doméstica ou para sair pela ligação de casa quando se está fora. Requer mais conhecimento técnico, mas elimina a dependência de terceiros.

# Instalar WireGuard (Debian/Ubuntu) $ sudo apt install wireguard # Gerar par de chaves $ wg genkey | tee privatekey | wg pubkey > publickey # Configuração do servidor (/etc/wireguard/wg0.conf) [Interface] Address = 10.8.0.1/24 ListenPort = 51820 PrivateKey = <chave-privada-do-servidor> [Peer] PublicKey = <chave-pública-do-cliente> AllowedIPs = 10.8.0.2/32

⚠️
A VPN não é uma solução mágica de privacidade

Uma VPN apenas desloca a confiança: em vez de confiar no seu ISP, passa a confiar no operador da VPN. Se o operador registar tráfego, cooperar com autoridades ou sofrer uma intrusão, a privacidade é perdida. A escolha de um operador com política no-logs auditada e jurisdição adequada é essencial.

03 — Servidores proxy

Proxies em detalhe

Um proxy é um servidor que intermedeia pedidos entre um cliente e um servidor de destino. Ao contrário de uma VPN, atua tipicamente a nível de aplicação e apenas no tráfego que lhe é explicitamente dirigido. Isso torna-o mais leve, mais específico e mais versátil.

Tipos de proxy por função

➡️

Forward Proxy

Intermedeia o cliente
  • O cliente configura-o explicitamente no browser ou sistema.
  • O servidor de destino vê o IP do proxy, não o do cliente.
  • Usado para anonimização, filtragem, cache.
  • Exemplos: Squid, Privoxy, proxies SOCKS5.
⬅️

Reverse Proxy

Intermedeia o servidor
  • Fica em frente de um ou mais servidores web.
  • Distribui carga, termina TLS, filtra pedidos.
  • O cliente pensa que fala diretamente com o servidor.
  • Exemplos: Nginx, HAProxy, Traefik, Caddy.
🎭

Transparent Proxy

Sem configuração do cliente
  • Interceta tráfego sem o cliente saber.
  • Configurado no gateway ou no router.
  • Usado em empresas, hotéis e ISPs.
  • Frequentemente combinado com filtragem de conteúdo.

Tipos de proxy por protocolo

01

HTTP/HTTPS proxy

O tipo mais comum. Intermedeia pedidos HTTP e HTTPS. Em HTTPS, o proxy só vê o destino (via CONNECT), não o conteúdo — a menos que faça inspeção TLS, o que requer instalar um certificado de confiança no cliente.

# Exemplo: pedido via proxy HTTP com curl $ curl -x http://proxy.empresa.pt:8080 https://exemplo.pt ^ o proxy recebe CONNECT exemplo.pt:443 e estabelece um túnel # Proxy com autenticação $ curl -x http://utilizador:password@proxy.empresa.pt:8080 https://exemplo.pt
02

SOCKS5 proxy

Opera a nível 4/5, encaminhando pacotes TCP e UDP sem interpretar a aplicação. Não entende HTTP, DNS ou outros protocolos — apenas transmite dados. É mais versátil que um proxy HTTP, mas não oferece cache nem filtragem de conteúdo.

# Exemplo: ligação SSH a funcionar como SOCKS5 (túnel dinâmico) $ ssh -D 1080 -N utilizador@servidor.remoto.pt # Depois, no browser ou noutra aplicação: # Host: localhost Porta: 1080 Tipo: SOCKS5 # Testar o túnel com curl $ curl --socks5 localhost:1080 https://ifconfig.me 203.0.113.55 ^ o pedido saiu pelo servidor remoto, não pela ligação local
03

Reverse proxy

Colocado em frente de servidores web, distribui carga, termina TLS, aplica regras de segurança e cache. É peça central de qualquer arquitetura web moderna. Não é "um proxy para o utilizador", mas "um proxy para o servidor".

# Exemplo: configuração de Nginx como reverse proxy server { listen 443 ssl http2; server_name exemplo.pt; ssl_certificate /etc/letsencrypt/live/exemplo.pt/fullchain.pem; ssl_certificate_key /etc/letsencrypt/live/exemplo.pt/privkey.pem; location / { proxy_pass http://127.0.0.1:3000; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; } }
04

Proxy residencial e proxy de datacenter

Proxies comerciais dividem-se em duas grandes categorias. Os de datacenter correm em servidores cloud e são rápidos mas facilmente identificáveis. Os residenciais usam IPs de ligações domésticas reais, tornando-se difíceis de bloquear — mas levantam questões éticas sobre consentimento dos utilizadores cujas ligações são usadas.

# Comparação de características Datacenter Rápido Barato Fácil de detetar Residencial Lento Caro Difícil de detetar ISP/Mobile Médio Caro Muito difícil de detetar
🔗
Proxy chains — proxies em cascata

É possível encadear vários proxies, de modo que cada um só conhece o anterior e o seguinte. O destino final vê apenas o último proxy da cadeia. É a ideia subjacente ao Tor, que usa três relays por circuito para separar quem pede, quem transmite e quem entrega.

04 — Comparação

VPN vs Proxy

A escolha entre VPN e proxy depende do que se pretende proteger ou contornar. Em muitas situações, a resposta correta é usar ambos — ou nenhum, se o modelo de ameaça não o justificar.

Critério VPN Proxy

Camada OSI L2/L3 L4/L7

Configuração Simples (a nível de sistema) Por aplicação, mais granular

Quando usar cada um?

🎯

Use VPN quando…

  • Precisa de proteger todo o tráfego do dispositivo, não só o browser.
  • Está numa rede pública (Wi-Fi de hotel, aeroporto) e quer cifra ponta-a-ponta até ao destino.
  • Trabalha em teletrabalho e precisa de aceder a recursos internos da empresa.
  • Quer que o seu IP público seja diferente face a todos os serviços.
  • Viaja frequentemente e quer uma experiência de rede consistente.
🎯

Use proxy quando…

  • Precisa de intermediação apenas para uma aplicação ou browser.
  • Quer cache para reduzir tráfego e acelerar acesso.
  • Precisa de filtrar conteúdo por categoria, URL ou palavra-chave.
  • Está a fazer scraping ou automação que requer rotação de IPs.
  • Precisa de inspecionar tráfego HTTP/HTTPS numa organização.
  • Quer fazer reverse proxy para balancear carga entre servidores.
🚨
Mitos frequentes

"VPN torna-me anónimo": falso. A VPN apenas substitui a confiança no ISP pela confiança no operador. Sem boas práticas de navegação, o anonimato é uma ilusão.
"HTTPS é suficiente, não preciso de VPN": parcialmente verdade para confidencialidade do conteúdo, mas o ISP continua a ver que sites visita e quando. A VPN esconde esse metadado.
"Proxy é mais rápido que VPN": depende. Sem cifra, sim; com inspeção TLS, um proxy pode ser tão lento quanto uma VPN mal configurada.
"VPN gratuita é igual a VPN paga": raramente. Se o produto é grátis, o produto é você — os dados de navegação são o modelo de negócio.

05 — Síntese

Boas práticas

Nem VPNs nem proxies são soluções mágicas. São ferramentas com pressupostos, limitações e riscos. Uma implementação descuidada pode dar falsa sensação de segurança ou até introduzir novas vulnerabilidades.

✅

Fazer

  • Escolher protocolos modernos: WireGuard, IKEv2, OpenVPN.
  • Verificar configurações: DNS leak, WebRTC leak, kill switch.
  • Ativar MFA no operador VPN: a conta é a chave do túnel.
  • Confiar em operadores auditados: com política no-logs verificada.
  • Preferir HTTPS sempre: a VPN não substitui o TLS.
  • Configurar SOCKS5 com autenticação: proxies abertos são um risco.
  • Documentar proxies internos: quem usa, para quê, com que regras.
  • Monitorizar logs de proxy: detetar abusos e falhas.
🚫

Evitar

  • Usar PPTP: obsoleto e inseguro, sem qualquer dúvida.
  • Confiar em VPNs gratuitas: o preço é frequentemente a sua privacidade.
  • Assumir anonimato total: metadados, cookies e fingerprinting persistem.
  • Ignorar vazamentos: DNS, IPv6 e WebRTC podem revelar o IP real.
  • Proxy aberto na internet: porta aberta para abusos e bloqueios.
  • Inspeção TLS sem transparência: quebra a confiança e a privacidade.
  • Deixar de usar TLS: "porque tenho VPN" é um erro grave.
  • Assumir que "VPN = segurança": é uma peça, não a solução.

Cenários práticos

💼 Trabalhador remoto a aceder a sistemas internos

VPN corporativa de acesso remoto com WireGuard ou IKEv2. Autenticação com certificados + MFA. Split tunneling configurado para que apenas o tráfego interno passe pelo túnel, mantendo o tráfego pessoal (streaming, redes sociais) na ligação local. Kill switch ativo para evitar fugas.

🛒 Empresa com filtragem de conteúdo e cache

Forward proxy (Squid) em modo transparente no gateway. Regras de categorias de sites bloqueados. Cache de objetos estáticos para poupar largura de banda. Logs centralizados. HTTPS tratado com CONNECT (sem inspeção) por omissão; inspeção TLS apenas para categorias específicas, com transparência para os utilizadores.

🌍 Jornalista a comunicar de região censurada

Combinação de Tor (cadeia de proxies) para navegação sensível, com VPN sobre Tor (VPN-over-Tor) para maior resiliência. Comunicações com fontes via Signal. Contas em serviços descartáveis. Verificações regulares de vazamentos. Plano de contingência com múltiplos canais.

verificação rápida — fugas e estado da VPN
$ # Ver IP público atual (deve ser o do servidor VPN quando ativa) $ curl -s https://ifconfig.me && echo 185.65.134.42 $ # Verificar DNS em uso (deve corresponder ao operador VPN) $ resolvectl status | grep "Current DNS" Current DNS Server: 10.64.0.1 ^ servidor DNS interno do operador VPN, não do ISP local $ # Verificar interfaces de rede ativas $ ip -brief addr lo UNKNOWN 127.0.0.1/8 ::1/128 wlan0 UP 192.168.1.42/24 wg0 UNKNOWN 10.8.0.2/32 ^ interface wg0 é o túnel WireGuard ativo $ # Testar se um proxy responde $ curl -x http://proxy.empresa.pt:8080 -sI https://exemplo.pt | head -1 HTTP/2 200 $ # Confirmar que o proxy está a ser usado (o IP visto deve ser o do proxy) $ curl -x http://proxy.empresa.pt:8080 -s https://ifconfig.me 203.0.113.5 ^ este é o IP de saída do proxy, não o do cliente

Para saber mais

Para VPNs, a documentação do WireGuard (wireguard.com) é excelente e concisa. O OpenVPN tem manuais completos em openvpn.net. Para proxies, o Squid (squid-cache.org) continua a ser a referência open source, e o Nginx (nginx.org) tem documentação detalhada sobre reverse proxy e terminação TLS. O livro "Tor: From the Dark Web to the Future of Privacy" de Ben Collier oferece contexto histórico e técnico sobre cadeias de proxies.
